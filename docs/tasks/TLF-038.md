## Findings (user playtest 2026-10-31, reproduced by tlf-lead in a windowed copy)

### A. The start feels "stuck" (Beat 01)
The game starts with the blocking monologue `EL_B01_01…03`. WASD does nothing until E has been pressed 3 times. The only cue is a small `[E] Continue` at the right edge of the box. The user thought the game was broken.

**Lead decision:**
- Beat 01 becomes **non-blocking with auto-advance** (≈ 4 s per line, like the device lines), and the player can walk right away. `EL_B01_04` (when picking up the watch) stays as specified.
- Beats 09 and 10 **stay blocking** (story climax), but the continue cue must be clear:
  - centred under the text, in the normal text size
  - gently pulsing/blinking (respect `reduced_effects`: no blinking, static instead)
  - text via `InputPrompts.format_prompt(&"confirm", ...)`, so the glyph matches the active device
- **Non-blocking dialogue doesn't consume `interact`:** today `DialogueBox._input` also advances non-blocking lines on `interact`, while the player uses the object in the same frame (polling). So E advances the text *and* uses the object. In non-blocking mode, only `confirm` and auto-advance advance the text; `interact` belongs to the world. In blocking mode `interact` keeps working (Opus's `dismiss_blocking_ui()` relies on it).
- **Movement hint:** if the player hasn't moved 3 s after the room starts, show a control hint (`UI_HINT_MOVE`, e.g. "Move: WASD / Left stick", glyph via InputPrompts). It disappears on the first movement and is shown only once per save (flag).

### B. Cyan square on Elias (`TargetHighlight/AbilityMarker`)
Cause: `TargetHighlight` is a `Node2D` under the HUD `CanvasLayer` (screen space), but `hud.gd:224` sets `global_position = target.global_position + Vector2(0, -28)`, a **world** coordinate. The camera offset is missing, so the marker floats somewhere on screen, often on Elias.

**Fix:**
- Convert world → screen (`target.get_global_transform_with_canvas().origin`, or `get_viewport().get_canvas_transform() * world_pos`), **or** move the marker into world space (e.g. as a child of the room/player, z above objects). Your choice; justify it.
- The marker sits above the targeted object, never on the player.
- Check whether the player itself (or the pocket-watch pickup at the spawn) is ever `current_target`. If so, that's a second bug: report it, and fix it if it's in an allowed file.

### C. Wrong feedback for `interact`
`E` on an object without a `use` interaction shows `UI_FB_UNSUPPORTED` "The pocket watch cannot affect this object." That's the watch-ability text, and wrong for `use`.

**Fix:**
- Map `unsupported` reasons from the `use` path (`player.gd::_handle_interaction`) to their own key `UI_FB_USE_UNSUPPORTED` ("Nothing happens.", or the like; ASCII). The watch keeps its text.
- Clean solution: an optional context in `UIFeedback.get_feedback_text(reason, context := &"watch")` or a separate function. Don't touch `InteractionService`.
- Check the interaction prompt on watch-only objects: if it shows `[E] Use`, the prompt should name the watch action instead (or no E prompt). List any deltas in the handoff.
